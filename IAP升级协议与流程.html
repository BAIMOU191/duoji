舵机 IAP 升级协议与流程

本文面向上位机开发人员，给出串口参数、帧格式、CRC、命令字段、升级文件解析、升级状态机、超时重试、掉电恢复和完整报文示例。所有多字节整数均为小端序。升级镜像为 AES-128-CTR 密文，上位机只负责按页透传，不需要密钥，也不做加解密。

固定升级行为：升级只保留有效参数页中的舵机ID和波特率档位；APP、全部用户参数均被清除，硬件信息页被擦除后由新APP按固件常量重建。新APP首次启动后使用保留的ID/波特率，其余参数采用新固件默认值。
升级文件与密钥：上位机使用出固件方用 fw_pack.py 打包出的加密升级文件 *_upgrade.bin（内含密文镜像）。AES-128 密钥只存在于出固件的电脑（gen_key.py 生成的 boot_key.txt 与 Boot 的 boot_key.h），上位机软件不需要、也不接触密钥。换密钥后烧着旧Boot的舵机将无法再升级。

一、接口与适用范围

项目APP阶段Boot阶段
物理接口单线半双工 UART，PC0，8数据位、无校验、1停止位
波特率舵机当前配置的波特率固定115200 bps
寻址命令数据第1字节为舵机ID；查询命令允许ID 255无ID字段，进入Boot后默认总线上只有目标设备
最大DATA长度8字节260字节
字节序所有16位、32位整数和CRC均低字节在前
收发方式一问一答。主机发送完成后切换为接收，收到对应应答或超时后再发送下一帧

波特率档位：1=9600、2=19200、3=38400、4=57600、5=115200、6=128000、7=256000、8=1000000。升级成功后APP恢复到升级前保留的档位；若升级前A/B参数页均无效且没有有效IAP快照，则新APP采用代码默认值：ID 0、档位5。

总线要求：建议升级时只连接一台舵机。Boot帧不含ID，多台设备同时停在Boot会同时应答并同时写入。广播查询ID 255也只能在单机连接时使用。
进入Boot前保存：APP先用当前波特率发完进入升级应答，再确认待保存参数写入Flash成功，保证Boot快照取得最新ID和波特率；保存失败时留在APP重试，不提前复位。
ID 255限制：ID 255只允许用于 CMD=20 查询实际ID。进入升级及升级脚本的 --id 参数必须使用0～254，不能使用广播ID 255。

二、通用帧格式

2CMD1请求命令；应答为请求命令按位或 80

三、CRC32算法

参数取值
算法CRC-32/ISO-HDLC，与Python zlib.crc32 一致
多项式反转值EDB88320
初值FFFFFFFF
输入/输出反射是
结果异或FFFFFFFF
发送顺序uint32小端序
 
def make_frame(cmd: int, data: bytes = b"") -> bytes:
    import struct, zlib
    body = bytes([cmd]) + struct.pack("<H", len(data)) + data
    crc = zlib.crc32(body) & 0xFFFFFFFF
    return b"\xAA\x55" + body + struct.pack("<I", crc) + b"\x55\xAA"

注意：CRC不包含帧头和帧尾；应答帧计算CRC时必须包含应答CMD、应答LEN以及状态码。同一算法也用于镜像明文校验（IMAGE_CRC32）和升级文件尾的文件CRC32。

四、APP阶段命令

APP阶段使用舵机当前波特率。错误ID、错误CRC、错误长度和未知命令均静默，不返回错误帧。

4.1 查询设备 CMD=20

用于确认目标ID、当前硬件身份和当前固件版本。

方向LENDATA偏移字段说明
请求10ID0～254为指定舵机；255为单机广播查询
成功应答90STATUS固定0
1实际ID设备当前ID
2～5硬件身份舵机类型、硬件版本、电压型号、扭矩型号
6～8固件版本主版本、次版本、修订版本

硬件信息页无效时，4字节硬件身份返回 FF FF FF FF。硬件版本以0.1版为单位，电压型号以V为单位，扭矩型号以kg·cm为单位。

4.2 进入升级 CMD=21

方向LENDATA偏移字段说明
请求80ID必须等于本机ID，不允许255
1～4当前硬件身份必须原样复制查询应答DATA[2～5]
5～7当前固件版本必须原样复制查询应答DATA[6～8]
成功应答10STATUS=0应答发送完成后，设备保存参数并软件复位进入Boot
关键点：进入升级命令携带的是“查询到的当前设备信息”，不是目标固件的信息。7字节不一致时返回状态2，设备不会复位。设备软件复位后Boot直接进入升级循环（不走200ms上电握手窗口），上位机切到115200后随时可握上。

五、Boot阶段命令

Boot固定115200 bps，不使用舵机ID。进入Boot后，上位机必须先握手，再依次执行开始、写页、完成。写页数据是升级文件中的密文，Boot自行解密。

5.1 握手 CMD=01

方向LENDATA偏移字段说明
请求0——无数据
成功应答60STATUS固定0
1升级状态0空白；1升级未完成；2升级完成；3状态页损坏
2～5硬件身份有效时为4项身份；硬件信息页被擦除或无效时为 FF FF FF FF

握手应答不包含Boot版本，也不包含舵机ID或波特率。

5.2 开始升级 CMD=02

方向LENDATA偏移字段类型与要求
请求200～3IMAGE_LENuint32；大于0、256字节对齐、不超过 E000（57344）
4～7IMAGE_CRC32对明文镜像计算的CRC32，取自升级文件头
8～19IV12字节解密初始值，取自升级文件头，每个升级文件不同
应答10STATUS0成功；3长度越界；4状态页写入校验失败

执行顺序：

  1. 提取保留身份：状态页已有未完成升级的有效快照时直接复用、不再重写；否则读取有效参数A页（A无效时用B页）的ID和波特率、硬件信息页的硬件身份（读不到时沿用旧快照或默认值），写入并校验IAP状态页，确保身份快照先落盘。
  2. 逐页擦除 1400～F6FF，即APP区、A/B参数页和硬件信息页；Boot区（0000～13FF）和IAP状态页不擦。
  3. 擦除完成后返回成功应答。

未完成升级的有效状态页会在重试时直接复用，不再次擦除。每次设备重新上电后，Boot的RAM状态会丢失，因此即使状态页显示“升级未完成”，上位机仍须重新发送开始命令。

5.3 写入一页 CMD=03

方向LENDATA偏移字段类型与要求
请求2600～3OFFSETuint32；256字节对齐，且小于IMAGE_LEN
4～259PAGE_CIPHER固定256字节，为升级文件偏移 32+OFFSET 起的密文，原样发送
应答50STATUS0成功；3偏移越界；4写入后读回校验失败；6尚未成功开始
1～4OFFSET原样返回请求偏移，用于匹配应答

Boot对目标页执行“解密→擦除→写入→逐字节读回比较”。同一页可重复发送（重发同一密文结果一致），页顺序不限。推荐按偏移从0递增写入，且每页收到状态0并确认返回偏移一致后再写下一页。

5.4 完成升级 CMD=04

方向LENDATA说明
请求0无必须在当前Boot会话成功执行开始命令后发送
应答1STATUS0成功；2固件类型不符；4完成标记校验失败；5整包CRC错误；6尚未开始

Boot先对偏移0开始的IMAGE_LEN字节明文计算整包CRC32并与IMAGE_CRC32比对，再检查偏移 0100 的固件信息块SVFW与设备硬件身份（硬件信息页，无效时用状态页中的快照）是否兼容。全部通过后写入完成标记、发送成功应答并直接跳转进入APP（不复位）。

六、状态码与静默规则

状态码含义上位机处理
0成功继续下一步
1帧无效（已知命令的LEN不对）检查组帧；Boot升级循环中可重发
2硬件身份或固件类型不匹配停止升级，选择正确机型固件
3镜像长度或写入偏移越界修正IMAGE_LEN、页对齐或OFFSET
4Flash写入后读回不一致重发当前命令；持续失败时检查供电与Flash
5明文整包CRC32不一致核对升级文件；重新发送全部页面后再发送完成
6顺序错误，当前Boot会话尚未成功开始重新发送开始命令
场景设备行为
APP阶段：错误CRC、错误ID、错误LEN、未知命令静默，不应答
Boot正常升级循环：错误CRC、未知命令（含CMD最高位为1的应答帧）静默丢弃，不应答
Boot正常升级循环：已知命令（01～04）但LEN不对返回状态1
Boot上电200ms握手窗口：非握手命令或坏帧静默，不延长窗口
收到CMD最高位为1的帧视为其他设备应答，静默丢弃

Boot的静默规则是为了避免多台舵机同时应答造成冲突；上位机不应把“无应答”当作CRC或命令错误的反馈，只按超时处理。

七、升级文件与固件信息块

7.1 升级文件格式（*_upgrade.bin）

升级文件由出固件方从APP的Intel HEX用 fw_pack.py 打包生成，上位机直接使用，不再解析HEX。文件格式（小端序）：

偏移长度字段说明
0～34文件标识ASCII SVUP
41格式版本当前为1，其他值拒绝升级
5～84适用硬件舵机类型、硬件版本、电压型号、扭矩型号；FF=不限
9～113固件版本主版本、次版本、修订版本
12～154IMAGE_LENuint32；明文镜像长度，256字节整数倍、非0、最大 E000
16～194IMAGE_CRC32明文镜像CRC32，Boot写完后核对
20～3112IVAES-128-CTR 初始值，每个升级文件随机生成
32IMAGE_LEN密文AES-128-CTR 加密后的镜像，写页时原样发送
32+IMAGE_LEN4文件CRC32对偏移0开始的全部前置字节计算，用于检测文件损坏

7.2 加密方式与上位机处理规则

加密算法为 AES-128-CTR：第 n 个16字节块的计数器 = IV(12字节) ‖ n(大端32位)，n = 镜像内偏移 ÷ 16。CTR 加解密互为逆运算，Boot 逐页解密后写入 Flash。

  • 上位机不解密、不加密、不需要密钥：把文件偏移32起的密文按256字节一页原样发送即可。
  • IMAGE_CRC32 是明文CRC，由Boot核对；上位机只透传该字段。
  • 上位机校验：文件标识 SVUP、格式版本=1、文件CRC32、密文长度=IMAGE_LEN、长度约束（256字节对齐、非0、≤ E000）。任一不符应拒绝升级。
  • 收到 .hex 明文固件应拒绝升级并提示先用 fw_pack.py 打包。
  • 同一升级文件的密文每次发送完全相同，重发页与首次发送字节一致，Boot先擦后写，重发安全。

7.3 固件信息块（SVFW）

APP镜像偏移 0100（绝对地址 1500）固定放置16字节固件信息块：

偏移长度字段说明
0～34MAGICASCII SVFW
41舵机类型FF 表示不限
51硬件版本FF 表示不限
61电压型号FF 表示不限
71扭矩型号FF 表示不限
8～103固件版本主版本、次版本、修订版本
11～155保留固定 FF

镜像加密后上位机无法直接读取该块，升级文件头已复制其中的适用硬件4项和固件版本3项，上位机用文件头核对机型和确认结果。Boot在完成命令中对解密后的镜像核对SVFW：MAGIC必须为 SVFW，4项逐一等于设备硬件身份或为 FF。设备硬件身份无法确定（空白）时不阻断，但应由生产流程保证固件正确。

系统只记录一个固件版本：信息块中的主、次、修订版本（与升级文件头一致）。协议本身没有版本字段，参数页也没有独立的协议版本或结构版本。

  1. 解析 *_upgrade.bin：校验SVUP标识、格式版本、文件CRC32和长度字段；取出适用硬件4项、固件版本3项、IMAGE_LEN、IMAGE_CRC32、IV和密文。
  2. 按用户提供的当前ID和APP波特率发送查询命令。
  3. 保存查询返回的实际ID、硬件身份和当前固件版本；用升级文件头的适用硬件4项核对机型（逐项相等或文件项为 FF）。

  5. 收到成功应答后立即把串口切换为115200，并循环发送Boot握手。
  6. 发送开始命令（携带IMAGE_LEN、IMAGE_CRC32和IV），等待擦除结束的成功应答。
  7. 从OFFSET=0开始逐页发送密文。每页收到状态0且返回OFFSET一致才进入下一页；失败重发同一页。
  8. 发送完成命令。收到状态0或应答超时后等待APP启动。
  9. 切回升级前APP波特率，使用升级前ID查询。读取到的固件版本必须等于升级文件头中的版本。

如果APP查询失败，上位机可切换到115200尝试Boot握手。握手成功说明设备已经停在Boot，可直接从开始命令重新升级。

9.1 救砖流程

  1. 总线上只保留目标舵机。
  2. 上位机打开115200串口并连续发送握手帧。
  3. 提示用户断电后重新上电。Boot在上电后的200ms窗口内只接受握手。
  4. 握手成功后执行开始、写页、完成。

救砖时无法查询ID和机型，完成后可用广播查询（ID 255）确认固件版本，仍只能单机连接。若APP区无效、升级状态未完成或状态页损坏，Boot不会跳入APP，会停留等待升级。

完成命令2s只发1次校验通过后Boot直接跳入APP；重发只会落到新APP上。超时不算失败，继续查询版本
等待新APP—先等待1.5s随后300ms超时查询，最多8次

APP接收半帧超过10ms没有新字节会丢弃；Boot接收半帧字节间隔超过50ms会丢弃。主机应一次写出完整帧，不应逐字节长延时发送。

Boot尚未开始升级、且已有可启动APP时，升级循环空闲10秒后自动返回APP；升级未完成时不会因空闲超时进入残缺APP。

十三、上位机参考代码

import struct, zlib

HEAD = b"\xAA\x55"
TAIL = b"\x55\xAA"
UP_HEAD = 32                      # 升级文件头长度

def crc32(data: bytes) -> int:
    return zlib.crc32(data) & 0xFFFFFFFF

def build_frame(cmd: int, data: bytes = b"") -> bytes:
    body = bytes([cmd]) + struct.pack("<H", len(data)) + data
    return HEAD + body + struct.pack("<I", crc32(body)) + TAIL

def parse_frame(frame: bytes, request_cmd: int):
    if len(frame) < 12 or frame[:2] != HEAD:
        raise ValueError("frame head/length")
    cmd = frame[2]
    length = struct.unpack_from("<H", frame, 3)[0]
    if len(frame) != 11 + length or frame[-2:] != TAIL:
        raise ValueError("frame boundary")
    body = frame[2:5 + length]
    received_crc = struct.unpack_from("<I", frame, 5 + length)[0]
    if received_crc != crc32(body):
        raise ValueError("frame crc")
    if cmd != (request_cmd | 0x80) or length < 1:
        raise ValueError("unexpected reply")
    status = frame[5]
    return status, frame[6:5 + length]

def load_upgrade(path: str):
    """读加密升级文件，返回 (密文, 适用硬件4项, 版本3项, 明文CRC32, IV)"""
    data = open(path, "rb").read()
    if len(data) < UP_HEAD + 4 or data[:4] != b"SVUP":
        raise ValueError("不是本产品的升级文件")
    if data[4] != 1:
        raise ValueError("升级文件格式版本不支持")
    if struct.unpack_from("<I", data, len(data) - 4)[0] != crc32(data[:-4]):
        raise ValueError("升级文件损坏(文件 CRC 不符)")
    length, image_crc = struct.unpack_from("<II", data, 12)
    cipher = data[UP_HEAD:-4]
    if length != len(cipher) or length == 0 or length % 256 or length > 0xE000:
        raise ValueError("升级文件长度字段不对")
    return cipher, tuple(data[5:9]), tuple(data[9:12]), image_crc, data[20:32]

def start_data(image_len: int, image_crc: int, iv: bytes) -> bytes:
    assert len(iv) == 12 and image_len and image_len % 256 == 0 and image_len <= 0xE000
    return struct.pack("<II", image_len, image_crc) + iv

def page_data(offset: int, cipher_page: bytes) -> bytes:
    assert offset % 256 == 0 and len(cipher_page) == 256
    return struct.pack("<I", offset) + cipher_page

串口适配器可能回显主机自己发送的请求。解析器应忽略CMD最高位为0的回显帧、其他命令的应答以及CRC错误帧，继续等待当前请求的对应应答。写页数据直接取 cipher[OFFSET:OFFSET+256] 原样发送，不需要密钥。

十四、上位机验收清单

  • 能够在APP当前波特率下按ID查询，并支持单机广播查询（仅查询允许255）。
  • 进入升级时原样回传查询得到的8字节设备信息（ID＋硬件身份4项＋版本3项）。
  • 进入Boot后切换到固定115200，不再发送舵机ID。
  • 解析 *_upgrade.bin：校验SVUP标识、格式版本1、文件CRC32和长度字段；不解密、不需要密钥。
  • 拒绝 .hex 明文固件；正确实现小端LEN、OFFSET、CRC32和IMAGE_LEN（256字节对齐、≤ E000）。
  • 用升级文件头的适用硬件4项与查询到的设备硬件身份核对机型（文件项为FF表示不限；设备返回FF FF FF FF时无法核对，需提示确认）。
  • 开始命令携带IMAGE_LEN、明文IMAGE_CRC32和12字节IV，DATA共20字节。
  • 写页发送密文原样；每页应答同时检查状态码和返回偏移；超时重发同一页。
  • 升级中断后重新发送开始（复用快照），并从第0页重发完整密文，不尝试直接完成。
  • 完成命令只发一次；超时后仍执行APP版本查询，避免把成功跳转误判为失败。
  • 最终在升级前保留的ID和波特率下查询到升级文件头中的固件版本，才判定升级成功。
  • 具备救砖路径：115200连续握手＋提示断电重上电。
